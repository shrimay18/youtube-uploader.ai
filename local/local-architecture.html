The local version

How the app works when it lives
on your own computer.

This is the original design. Everything runs on your machine. Your secret keys never leave. Read top-to-bottom — every idea is explained like you're in school, and every big decision has a box you can quote in an interview.

Python + FlaskReactRuns on localhost:8765Encrypted local vaultSingle userZero-knowledge

1What is this thing?

You give it a video. It writes the perfect YouTube title, description, tags, chapters and thumbnail (the stuff that helps a video get found), and then it can upload the video to your YouTube channel for you.

🧒 In plain English

Imagine a super-smart helper who watches your video, listens to it, figures out what people are searching for on YouTube, and writes all the "packaging" so your video shows up in search. Then it posts it for you. In the local version, this whole helper lives inside your computer — like an app you installed, not a website.

It's made of two halves that talk to each other:

  • The frontend — the buttons and screens you see (built with React).
  • The backend — the "engine" that does the real work (built with Python + Flask).

🎓 Why build it "local-first"?

The promise: "your secret keys never leave your device." That's a real privacy selling point. Because the engine runs on your machine, your API keys and YouTube passwords-of-sorts (tokens) are only ever on your disk — we (the makers) literally cannot see them. Interview line: "Local-first gave us a genuine zero-knowledge privacy guarantee — there's no server that ever holds user secrets."

3The frontend — the part you click

Built with React (a popular way to build web screens) and Vite (a tool that bundles it into fast files). The finished files live in frontend/dist.

🧒 In plain English

React is like LEGO for web pages — you build small blocks (a button, a card, a modal) and snap them together. Vite is the machine that packs all those blocks into a neat box the browser can open quickly.

Here's the clever part: the backend also serves the frontend. When you open localhost:8765, the Flask server hands you the React files. So you only run one thing, and the screens + engine come together.

🎓 Why serve the frontend from the backend?

One process to start, no separate web server, and the browser talks to the API on the same address (no cross-origin headaches). Great for a desktop-style local app.

4The backend — the engine (Flask)

You start it with one command: python -m youtube_manager serve. That boots a Flask web server on port 8765 that: (1) serves the React screens, and (2) answers API requests like "make me a draft" or "publish this."

🧒 In plain English

Flask is a small, friendly Python tool for making a web server. Think of it as a waiter: the browser asks for something (/api/generate), the waiter (Flask) takes the order to the kitchen (the pipeline), and brings back the result.

An API is just a set of "doors" (URLs) the frontend can knock on. Examples in this app:

Door (URL)What it does
/api/generateStart making a draft from a video
/api/jobs/<id>Check "is my draft ready yet?"
/api/drafts/<slug>/publishUpload the finished video to YouTube
/api/settings/keysSave/read your AI keys (masked)

5The vault — the secret safe 🔐

Your AI keys and YouTube tokens are secrets. The vault (vault.py) locks them up so nobody — not even someone who steals your laptop file — can read them without your password.

🧒 In plain English

Imagine a safe. The safe scrambles your keys into gibberish (encryption). To scramble/unscramble, you need a special "safe key." Where does the safe key come from?

  • Password accounts: the safe key is made from your password using a recipe called scrypt. No password → no safe key → the gibberish stays gibberish. (That's also why there's no password recovery — even we can't open it.)
  • Google accounts: the safe key is a random key stored in your operating system's keychain (Windows Credential Manager), which only unlocks when you're logged into your computer.

The actual scrambling uses Fernet (a well-tested encryption method). The secrets sit encrypted in a file called account.json.

🎓 Why scrypt + Fernet + OS keychain?

Fernet = a safe, standard "encrypt this string" tool (AES under the hood) so we don't invent our own crypto. scrypt = turns a human password into a strong key and is deliberately slow, so a hacker can't guess millions of passwords quickly. OS keychain = for Google logins there's no password to derive from, so we lean on the operating system's secure storage. Interview line: "We never store the encryption key next to the data; it's derived from the user's password or kept in the OS keychain — so the on-disk file alone is useless to an attacker."

6Logging in (single user)

Because the app runs on your machine, there's really only one user: you. You sign in (with a password or "Continue with Google"), and that unlocks the vault for this session. The unlocked keys are kept in memory while the app runs.

🧒 In plain English

Signing in is like opening the safe for the day. While it's open, the engine can grab your keys to do work. Close the app (or log out) and the safe locks again.

Google sign-in uses Supabase (a hosted service) just to prove "yes, this is really you." Even then, the keys stay local — Supabase only helps with the login handshake.

Stage 2: Transcribe (the ears 👂)

It pulls the audio out with ffmpeg (a tool that handles audio/video), then uses faster-whisper (a speech-to-text AI that runs on your computer) to turn speech into text — with timestamps, so we can auto-build chapters.

🎓 Why faster-whisper (local speech-to-text)?

It's free, private (audio never leaves your machine), and good. On a GPU it's ~45× real-time. Interview line: "We used a local Whisper model so transcription stays free and private — no per-minute API bill and no audio leaving the device."

Stage 3: Research (the detective 🔎)

It figures out what's already ranking for your topic — using free signals like YouTube autocomplete, Google Trends, and the YouTube Data API (to see the titles/tags of top videos). This is what makes the writing rank, instead of being generic AI mush.

Stage 4: Generate (the writer ✍️)

An LLM (a text-writing AI like Gemini) reads the transcript + the research and writes candidate titles, a description, tags, chapters, and a pinned comment. Then a local SEO scorer (seo.py, plain math, no AI, so it's free and predictable) scores each title 0–100 and picks the best.

🎓 Why a local scorer instead of asking the AI to rate itself?

AIs are bad, biased judges of their own work and it costs another API call. A deterministic scorer (length, keyword placement, ranking-word coverage) is free, fast, and repeatable. Interview line: "We score titles with a local, deterministic function against real ranking vocabulary — cheaper and more trustworthy than self-evaluation."

8The AI brains — providers & fallback

The app can use several AI providers (Gemini, Groq, OpenAI, Claude). They all hide behind one common shape (an interface) so the rest of the code doesn't care which one it's talking to.

🧒 In plain English

Two clever tricks:

1) Many keys, auto-rotate. Each provider can hold several API keys. Free keys run out ("quota"). If key #1 is exhausted, it quietly tries key #2, then #3. Like a singer losing their voice — the backup singer steps in.

2) Provider fallback chain. You set an order (say Claude → Gemini → Groq). If Claude is out of quota, it falls to Gemini, then Groq, without you noticing.

# the heart of key rotation (providers/base.py), simplified
for key in self.keys:
    try: return self._call(key, system, user)   # worked!
    except QuotaExceeded: continue          # this key is spent → next
🎓 Why the interface + fallback design? (This is textbook SOLID.)

Adding a new AI provider = writing one new class; nothing else changes. That's the Open/Closed Principle ("open to extension, closed to modification"). Swapping providers freely is the Liskov idea (any provider works wherever the interface is expected). Interview line: "Providers sit behind a common interface with a fallback chain, so adding one is a new class and the pipeline never changes — classic OCP/LSP."

9Connecting YouTube (giving a valet key 🅿️)

To upload to your channel, the app needs your permission. That's OAuth — you click "Connect", a Google window opens, you approve, and Google hands the app a token (a temporary "valet key") that lets it upload only to that channel.

🧒 In plain English

A valet key lets someone park your car but not open the trunk. The YouTube token lets the app upload videos to your channel but nothing more, and you can revoke it anytime.

In the local app, this uses a "loopback" flow: Google redirects back to a tiny web address on your own computer. (Remember this detail — it's exactly what can't work on a hosted server, and it's why the production version rebuilds this part.)

You can connect multiple channels and publish one video to several at once — each channel keeps its own token.

10Follow one click: "Generate a draft"

Let's trace exactly what happens in the code when you click Generate. This is the kind of end-to-end story interviewers love.

Browser sends your video link to POST /api/generate.
Flask creates a "job" and starts it on a background thread (so your screen doesn't freeze). It returns a job_id instantly.
The thread calls pipeline.build_draft(...) — the assembly line.
Ingest downloads/locates the video → transcribe (ffmpeg + Whisper) → research (YouTube API + trends) → generate (LLM writes, SEO scorer picks the best title).
The finished draft is saved as a draft.yaml file, and the job is marked done.
Meanwhile the browser keeps asking GET /api/jobs/<id> ("ready yet?") every 1.5s until it says done — then shows you the draft to review.
⚠️ Remember this: jobs run on in-process threads

The work happens on a thread inside the web server, and the job list lives in memory. That's totally fine for one person on one computer. But it becomes a problem when many people share one server (a thread can clobber another, and a restart loses jobs). Hold that thought for the production handbook.

11Why your stuff is safe (zero-knowledge)

  • Keys and tokens are encrypted on your disk; the encryption key comes from your password or the OS keychain — never stored next to the data.
  • AI requests go straight from your machine to the AI provider using your own key. We're never in the middle.
  • The only thing that touches our (Supabase) servers is the login handshake and anonymous usage counts (no content, no keys).
🎓 Interview summary of the security model

"It's zero-knowledge by construction: the sensitive data physically never leaves the device, and even the on-disk copy is encrypted with a key we never possess."

12The choices, for interviews 🎓

A cheat-sheet of every big decision — what, why, and the one-liner to say.

Local-firstGenuine privacy ("keys never leave your device") and $0 to run — the user's machine does the work.
FlaskTiny, simple Python web server; perfect for a single-user local app that also serves the React files.
Fernet + scrypt + OS keychainStandard, audited encryption; the key is derived from the password or kept by the OS — never stored beside the data.

13Where the local model hits a wall 🧱

The local design is lovely for privacy — but it forces every user to install and run the app. That kills the "just visit a link and start" dream. And a few things simply can't work on a shared server the way they do locally:

  • The vault assumes one user + the OS keychain — no good for many users on one server.
  • YouTube's loopback OAuth only works on a device, not a server.
  • Jobs on threads + in-memory don't survive a shared, restarting server.
  • Whisper needs a beefy machine per user.
🧒 So what next?

To let anyone use it by just visiting a website, we re-architect it into a hosted SaaS. That's a whole separate story — with a different set of trade-offs and choices. It's in the production handbook (the other folder).
