The production version

Turning the app into a website
anyone can just visit.

The local app was private but you had to install it. To let anyone use it from a link, we rebuilt it as a hosted, multi-tenant SaaS. This handbook explains every new part, the trade-offs, the YouTube quota math, and the reasoning — all in plain language and interview-ready.

1Why change everything?

The local app is great, but it has one deal-breaker: every user must download and run it. Most people won't. The dream is: click a link, sign in, go. That means the engine has to live on our server, not the user's computer.

🧒 In plain English

Local = the helper lives in your house. Very private, but you had to build the house first. Hosted (SaaS) = the helper lives in a shared building you visit through a website. Way easier for everyone — but now the helper is holding your keys in that building, so we have to lock them up really well.

⚠️ The honest trade-off (say this in interviews)

The local promise "your keys never leave your device" cannot be literally true in a hosted app — there's no local engine anymore. So the promise changes to: "your keys are encrypted at rest on our servers and we never read them." We even had to rewrite the privacy policy to say this before applying for YouTube's audit. Recognizing and owning that trade-off is the mature engineering answer.

"Multi-tenant" just means: many users ("tenants") share one server, but each only ever sees their own data. That one idea drives almost every decision below.

🧒 Who does what?
  • Vercel hosts only the screens (static files). It's free and fast, but it cannot run heavy Python, ffmpeg, or long jobs — that's why the engine lives elsewhere.
  • Oracle VM is a small always-on computer in the cloud that runs the real Python engine 24/7.
  • Supabase is the shared filing cabinet (a Postgres database) where each user's encrypted keys, tokens and usage are stored.

P1

Server-side encrypted keys + JWT login

Store each user's secrets safely on the server, and prove who's asking on every request.

Two problems to solve at once: (1) where do secrets live now that there's no device vault, and (2) how does the server know which user is calling?

The login ticket (JWT)

🧒 In plain English — the coat check

When you sign in with Google (via Supabase), you get a JWT — think of it as a numbered coat-check ticket that's impossible to forge (it's cryptographically signed). Every time your browser asks the server to do something, it shows the ticket (Authorization: Bearer <token>). The server checks the signature, reads "this is user #42", and only touches user #42's data.

# auth_web.py — every request turns a token into a user (simplified)
def context_from_request(request, key_service):
    token = bearer_token(request)                 # pull the ticket
    claims = supabase_auth.verify(token)          # is it real? (JWKS/ES256)
    return key_service.build_context(claims.user_id)  # load THAT user's keys
🎓 Why JWT / stateless auth?

The local app kept the logged-in user in a global variable (vault._STATE). With many users on one server that's a disaster — request A could overwrite request B's identity. A JWT is stateless: the identity travels with each request, so two users are never confused, and we can add more servers later without a shared login memory. Interview line: "We removed global mutable state and made auth per-request/stateless via signed JWTs — the multi-tenant-safe pattern."

Locking the keys (KeyCrypto + KeyStore + KeyService)

🧒 In plain English — the locked drawer

Keys are scrambled with Fernet using one master key (TM_MASTER_KEY) that lives only in the server's environment — never in the database, never in the browser. So even someone who copies the whole database gets only gibberish. The user only ever sees a masked version (like AIzaSy…tgs).

Three small classes, each with one job:

  • KeyCrypto — the scrambler: .enc() / .dec().
  • KeyStore — where rows live. It's an interface with two bodies: InMemoryKeyStore (for tests) and SupabaseKeyStore (real database).
  • KeyService — the brain that ties them together: save, list-masked, and build the per-user context.
🎓 Why split into three (and an interface)?

Single Responsibility: each class does one thing. The KeyStore interface means the same logic runs against a fake in-memory store in tests and Supabase in production — that's Dependency Inversion (depend on an interface, not a concrete database). Interview line: "Storage is behind an interface, so tests use an in-memory store and prod uses Supabase without changing a line of business logic."

UserContext replaces the old global vault: a plain object holding this user's keys and provider order, passed into get_provider_for(ctx, settings). No globals anywhere.

P2

Web YouTube OAuth + the quota story

Connect channels from a real website, and deal with YouTube's strict upload limit.

The local app used a "loopback" that only works on your own machine. On a server we use the proper web OAuth flow: Google redirects back to https://api.yourdomain/api/youtube/oauth/callback, we swap the code for a refresh token, and store it encrypted per channel.

The quota problem (the important one 📉)

⚠️ YouTube's brutal math
Free quota per Google project = 10,000 units / day
One upload (videos.insert) = 1,600 units
10,000 ÷ 1,600 ≈ 6 uploads / DAY — for the WHOLE website, not per user.
🧒 In plain English

Every day the whole site shares a bucket that only allows ~6 uploads total. And a common "fix" doesn't work: API keys can only READ (search videos, read stats). Uploads need OAuth, and the upload cost is charged to whoever's Google project the login belongs to. So adding more API keys gives more research room, but zero extra uploads. We verified this and did not build a useless "per-user upload key" column.

The solution: shared bucket, then bring-your-own

This is uploadrouting.run_with_quota_fallback: for a single upload it tries the app's client, and on a 403 quotaExceeded it falls back to the user's own OAuth client (which they add through a guided wizard: create project → enable API → make OAuth client → paste 2 values). Bulk uploads are always BYO, so heavy users never drain the free bucket for everyone.

🎓 Why this model?

It keeps the product free and instant for casual users (they never even see the wizard) while making power users self-fund their own quota — and it's honest about a hard platform limit instead of pretending to beat it. Interview line: "We route uploads through a shared pool with graceful BYO-credential fallback, because upload quota is charged to the OAuth client's project and can't be multiplied with API keys."

Each channel remembers which client authorized it (keyed by user_id, channel_id, client_kind) so a channel can hold both an "app" and a "user" connection and we always charge the right bucket.

P3

Transcription API + a real job queue

Stop relying on the user's CPU, and stop doing heavy work inside the web request.

Transcription (the ears, moved to the cloud)

Local Whisper needs a beefy machine per user — impossible when everyone shares one small server. So transcriber.py puts transcription behind an interface with swappable bodies: Deepgram, OpenAI, or still-local Whisper, chosen by an env var TM_TRANSCRIBER. All return the exact same Transcript shape, so the pipeline doesn't change.

🎓 Why an interface with three bodies?

Same DIP idea as storage: we can start cheap (local Whisper on the VM), and flip a single env var to a paid API if the server gets busy — no code change. Interview line: "Transcription is a pluggable port; we pick the adapter by config, trading cost vs. server load without touching the pipeline."

The job queue (a proper to-do list)

🧒 In plain English

Local jobs ran on a thread inside the web server and the job list lived in memory — fine for one person, dangerous for many (a restart loses everything; heavy work blocks the server). The fix is a classic pattern: the web server just writes a note ("transcribe video X") onto a shared to-do list (Redis), and a separate worker process picks notes off and does the heavy lifting.

jobqueue.py keeps the same interface with InMemoryJobQueue (threads, for tests) and RQJobQueue (Redis, for production), picked by whether REDIS_URL is set.

🎓 Why split web from worker?

The web server stays fast and responsive (it never blocks on a 3-minute transcription), heavy work survives restarts and retries, and you can scale workers independently. Interview line: "We moved long-running work off the request path onto a Redis-backed queue with a separate worker — the standard way to keep a web tier responsive and resilient."

P4

Deploy: where it all runs

Free, always-on hosting + HTTPS + the browser-to-server plumbing.

  • Frontend → Vercel (free static hosting). It's given one setting, VITE_API_URL, so it knows where the backend lives, and it sends the JWT on every call.
  • Backend → Oracle Cloud Always-Free VM running gunicorn (the production web engine, via wsgi.py) + the rq worker (worker.py) + Redis + ffmpeg, kept alive by systemd, with HTTPS auto-provisioned by Caddy.
  • CORS — because the frontend (vercel.app) and backend (your domain) are different origins, the backend must explicitly allow the frontend. That's the env-gated TM_ALLOWED_ORIGIN block (inert locally, on in production).
🎓 Why Oracle Always-Free instead of Render/Railway?

We need 24/7 uptime, real CPU/RAM for ffmpeg + transcription, and a separate worker — all for $0. Render's free tier sleeps after 15 min, gives only 512MB/0.1 CPU (too small for ffmpeg), and its worker is paid. Pinging it to stay awake doesn't fix the resource ceiling. Oracle's Ampere A1 free tier is genuinely always-on with 4 cores / 24 GB. Interview line: "We chose Oracle Always-Free because the workload needs a persistent, non-sleeping box with enough CPU for media processing and a background worker — the free PaaS tiers sleep and are resource-capped."

🧒 What's WSGI / gunicorn?

Flask's built-in server is a toy for development. gunicorn is the grown-up server that runs many workers, handles real traffic, and restarts cleanly. WSGI is just the standard "plug" (wsgi.py) that lets gunicorn start your Flask app.

4Follow one click: "Publish this video" (hosted)

Browser calls POST /api/drafts/<slug>/publish with the JWT in the header.
before_request verifies the JWT → builds the UserContext for that user (their keys, their channels).
The server enqueues an upload job to Redis and instantly returns a job_id (no waiting).
The worker picks it up, downloads the source video to a temp dir, and calls run_with_quota_fallback: try the app's shared client → on 403 quotaExceeded, use the user's own client.
YouTube accepts the upload; we set title/description/tags/thumbnail, optional pinned comment, save the result, and delete the source video (privacy).
Browser polls the job → shows "Published ✓" with the new video link.

5How we kept the code clean (SOLID)

Interviewers love SOLID. Here's where each principle actually shows up in this codebase — with a real example, not a textbook definition.

PrincipleWhere it lives here
S — Single ResponsibilityKeyCrypto only encrypts, KeyStore only persists, KeyService only orchestrates. Each has one reason to change.
O — Open/ClosedAdd a new AI provider or transcriber = a new class; existing code is untouched.
L — LiskovAny Transcriber / Provider body is a drop-in for its interface; the pipeline can't tell which one it got.
I — Interface SegregationSmall, focused ABCs (KeyStore, ChannelStore, JobQueue) instead of one giant "store everything" class.
D — Dependency InversionServices depend on the interface; we inject InMemory* in tests and Supabase* in prod. This is the single biggest win of the rebuild.
✅ The one-sentence version

"Every external thing — the database, YouTube, the AI, transcription, the job runner — sits behind a small interface, so the core logic never depends on a vendor and is fully testable with fakes."

664 tests (why we wrote them first)

The whole rebuild was done test-first: 64 tests cover key rotation, the SEO scorer, config parsing, YouTube key rotation, the KeyService (masked view never leaks the raw key, users are isolated, data persists), OAuth URL building + code exchange, upload routing/fallback, the channel stores, transcriber parsing, and the job queue.

🧒 Why bother?

Because we rebuilt the foundations while the local app still had to keep working. Tests are a safety net: they let us change scary things (auth, encryption, uploads) and instantly know if we broke something. The in-memory fakes (thanks to DIP above) mean tests run in milliseconds with no real database or network.

🎓 Interview line

"I built the SaaS foundations behind interfaces specifically so they'd be unit-testable with in-memory doubles — 64 fast tests gave me the confidence to rewire auth and uploads without a live server."

7Privacy & the YouTube audit

Uploading on a user's behalf uses a sensitive YouTube scope (youtube.force-ssl), which Google audits before letting more than 100 people use it. Two things had to be true:

  • Honest privacy policy. We rewrote it from the local "stays on your device / nothing touches our servers" to the hosted truth: "encrypted at rest on our servers, we never read it, source videos deleted after processing." It also carries Google's required Limited Use disclosure and a revoke-access link.
  • Least privilege. We ask for exactly one scope, only to do what the user clicks (upload + set metadata + optional pinned comment), and store the token encrypted.
⚠️ Why this mattered

Shipping the old "never touches our servers" copy while actually storing keys server-side would be false — an instant audit failure (and dishonest). Fixing the copy first was a compliance blocker we cleared before anything else.
